## 2026-08-21｜脱离任务栏嵌入时重建歌词窗口以恢复浮动合成

### 变更目的

修复"开启任务栏嵌入后关闭嵌入，歌词窗口不可见"的问题。系统排查（纯 WPF 透明窗口探针、WinForms TransparencyKey 探针、独立往返探针 4 种变体、外部样式/可见性/父子中转干预）证实根因：跨进程 `SetParent` 将 WPF 分层窗口（`AllowsTransparency`）挂入任务栏后，该 HWND 的 DWM 分层合成表面被永久失效——窗口内容仍在（`PrintWindow` 表面有内容、样式/边界/可见性全部正常），但作为顶层窗口 DWM 永不合成（嵌入态可见仅因 WebView2 子窗口自绘）。任何样式翻转、顺序调整、隐藏重显、进程内窗口中转均无法复活该表面；唯一可靠恢复方式是更换 HWND。

### 用户影响

- 关闭任务栏嵌入后，歌词窗口以新建窗口回退到浮动透明模式，正常可见；此前该窗口会"消失"（内容存在但不合成）。
- 嵌入模式下 Explorer 重启等导致附着失效回退浮动时，同样通过重建窗口保证可见。
- 反复"开启嵌入→关闭嵌入"可稳定往返；重建窗口会重新初始化 WebView2 与歌词管线（约一秒内完成），歌词显示短暂中断后恢复。
- 其余行为（嵌入定位、多显示器镜像、设置持久化）不变。

### 技术说明

- `EmbeddedTaskbarAnchor` 暴露 `IsAttached`；`MainWindow.AnchorToTaskbar` 统一管理脱离：已建立嵌入的窗口在回退浮动前触发新增的 `RecreateWindowRequested` 事件，不再复用受损 HWND。
- `LyricsWindowHost` 将窗口事件接线重构为 `CreateAndWireLyricsWindow`/`UnwireLyricsWindow`，并新增 `RecreateLyricsWindow`：在歌词 STA 线程上关闭旧窗口（`CloseForRecreation` 绕过用户隐藏语义、仍走完整 `Dispose`）、创建新 `MainWindow`、重放当前设置并按需显示。
- `ReconcileMirrorWindows` 在关闭嵌入时替换已嵌入的镜像窗口；`LyricsMirrorWindow` 暴露 `IsEmbeddedInTaskbar`。
- 此前一次基于"首次渲染前不嵌入"的门控尝试经往返探针证伪后已移除。

### 兼容性

- 未修改 `settings.json`、WebView V1 消息、缓存与发布结构。窗口重建为进程内行为，对外不可见。

### 验证

- 运行时往返验证（UIA 驱动真实设置开关）：嵌入可见（screenBright 639）→ 关闭嵌入 → 新 HWND 浮动窗口立即可见（639）；再开启（嵌入左锚点 x=0）→ 再关闭 → 再次新 HWND 可见；旧窗口表面内容、DWM 状态在受损态的对照数据一并归档。
- 探针实验：纯 WPF 分层窗口跨进程嵌入后顶层合成永久失效（4 种脱离变体与进程内中转均无效）；系统分层合成健康（对照探针可见 9661/13200）。
- 定向验证通过：EmbeddedTaskbar 相关 App 测试 23/23。完整验证通过：Web 62/62、App 220/220、Core 134/134、Settings 契约、代码格式、输出与重启脚本回归；日志位于 `tmp/verify-logs/20260821-153116057-30004-0a192cfb1dde4bdbbb91df33f0e87b95/`。

## 2026-08-21｜统一浮动与任务栏嵌入模式的水平锚点

### 变更目的

消除"设置水平锚点为左侧后，开启任务栏嵌入歌词却出现在任务栏右侧"的困惑。此前存在两个互不相通的水平锚点设置：显示与外观面板的"水平锚点"（默认 Left）只作用于浮动模式，任务栏嵌入面板另有"嵌入水平锚点"（默认 Right）只作用于嵌入模式；用户在显示面板改为左侧后，嵌入模式仍按默认右侧定位。经用户确认，将两个锚点统一为单一设置。

### 用户影响

- "水平锚点"现在同时决定浮动模式与任务栏嵌入模式的水平位置；任务栏嵌入面板不再显示独立的锚点选择。
- 嵌入模式默认位置由右侧改为左侧（跟随水平锚点默认值 Left），不再覆盖系统托盘区域。
- 嵌入宽度、水平偏移、垂直偏移设置保持独立不变。
- 旧 `settings.json` 中的 `EmbeddedTaskbarHorizontalAnchor` 字段：读取时被安全忽略，下次保存时自动从文件中移除。

### 技术说明

- 删除 `EmbeddedTaskbarHorizontalAnchor` 枚举、`AppSettings.EmbeddedTaskbarHorizontalAnchor` 属性、其规范化分支、设置窗口状态同步/更新/复制路径、设置页 HTML 控件与 JS 选项。
- `EmbeddedTaskbarLayoutCalculator.CalculateHorizontalLeft` 改用 `LyricsHorizontalAnchor`；`EmbeddedTaskbarAnchor.Position` 使用 `settings.HorizontalAnchor`。
- `HorizontalAnchor` 变化经由既有 `WindowLayoutChanged` 变更集触发 `AnchorToTaskbar`，嵌入窗口在浮动窗口与镜像窗口中同步重新定位。
- 设置契约测试的键清单与 AppSettings 属性断言同步更新；新增变更集测试：水平锚点变化必须触发歌词窗口重应用。

### 兼容性

- `settings.json` 移除一个字段（读取安全降级、保存收敛为规范形式），其余字段、WebView V1 消息、缓存与发布结构不变。
- WebView 设置协议仅减少一个 `update` 消息键，无新增或变更类型。

### 验证

- 运行时验证：保留旧字段的 `settings.json` 启动安全；嵌入窗口定位在任务栏左缘（x=0）；UIA 切换嵌入关闭/开启往返后位置保持左侧；保存后旧字段从文件移除。

## 2026-08-21｜修复任务栏嵌入从未真正成功导致的持续闪烁

### 变更目的

定位并消除开启任务栏嵌入后显示区域持续闪烁的真正根因。前一条记录消除了"定位失败即退出嵌入"的回退振荡，但用户实测闪烁仍在。通过原生窗口状态高频采样与临时插桩日志复现发现：`EmbeddedTaskbarAnchor.Attach` 中 `SetParent` 实际成功后，紧接的 `GetParent(hwnd) != parent` 校验恒为真——Win32 规定无 `WS_CHILD` 样式的窗口 `GetParent` 返回 owner（此处为 NULL）而非 `SetParent` 所设父窗口，而 `WS_CHILD` 样式在校验之后才由 `ApplyChildWindowStyle` 添加。于是每轮附着都误报失败：调用方执行 `Detach`（`SetParent` 回桌面）并回退浮动定位；每次父子关系切换又触发 `WM_SHOWWINDOW`，`WndProc` 重连逻辑再次发起 `AnchorToTaskbar`，形成约 10ms 周期、不依赖 60ms 轮询的自激风暴。窗口在"任务栏子窗口（坐标被按客户区解释，落到屏幕外）"与"顶层浮动窗口"间高频切换，即为用户所见闪烁。

### 用户影响

- 任务栏嵌入首次真正生效：歌词窗口稳定附着在任务栏内，按设置的水平锚点（左/中/右）与偏移精确定位，垂直居中。
- 嵌入期间不再出现位置跳动、可见性闪烁或嵌入/浮动状态来回切换。
- 关闭嵌入、退出应用时回退浮动透明窗口的行为不变。

### 技术说明

- `Attach` 的父窗口校验与既有附着有效性校验改用 `GetAncestor(hwnd, GA_PARENT)`，该 API 不依赖 `WS_CHILD` 样式即可返回真实父窗口；`SetParent` 后先应用子窗口样式再校验。
- `Position` 将 WPF `Window.Left`/`Top` 同步为任务栏客户区 DIP 坐标（带变化守卫），防止 WPF 布局系统在后续布局提交时把浮动模式的屏幕坐标当作客户区坐标写回，与嵌入定位互相争抢。
- 移除全部临时诊断插桩；`GetParent` 互操作声明因不再使用而删除。

### 兼容性

- 未修改 `settings.json` 字段、WebView V1 消息、缓存格式与发布结构。
- 嵌入状态判定仅影响 App 内部原生附着逻辑；浮动模式、多显示器镜像窗口共用同一附着代码路径，行为一并修复。

### 验证

- 运行时原生采样（50ms×6 秒，修复前 4 种状态每 40-100ms 振荡；修复后 150/150 采样完全一致：右锚点 x=2240、客户区 y=2、可见性与样式恒定），插桩日志确认风暴链路为 `SetParent` 成功 → `GetParent` 误报 → `Detach` → `WM_SHOWWINDOW` 重连循环。
- 定向验证通过：EmbeddedTaskbar 相关 App 测试 23/23。
- 完整验证通过：Web 62/62、App 219/219、Core 134/134、Settings 契约、代码格式、验证输出与重启脚本回归；日志位于 `tmp/verify-logs/20260821-121206057-44816-b4adbc19891c4b66826c6d368e68554a/`。
- 零警告构建与 `git diff --check` 见交接说明。

### 后续事项

- 人工验证多显示器（镜像窗口嵌入副屏任务栏）、Explorer 重启、DPI 切换及关闭嵌入回退浮动窗口的表现。

## 2026-08-21｜稳定任务栏嵌入失败恢复并消除周期性闪烁

### 变更目的

修复开启任务栏嵌入后显示区域周期性闪烁的问题。选择性合入 PR #38 时，`EmbeddedTaskbarAnchor.Attach` 被改为返回原生定位结果；主窗口和镜像窗口随后把一次 `SetWindowPos` 失败视为整个嵌入失败，在每 `60ms` 的可见性保障路径中反复执行“解除任务栏父子关系、回退透明窗口、重新嵌入”。本次将“任务栏不可用”和“已经嵌入但本轮定位待重试”分开处理，同时保留前一阶段加入的相同布局原生调用去重。

### 用户影响

- 已成功建立任务栏父子关系后，单次定位失败不会再退出嵌入模式；后续轮询会在原父窗口中继续重试，避免嵌入窗口与透明顶层窗口之间来回切换。
- 首次附着确实不可用、目标显示器改变、任务栏父窗口失效或嵌入被关闭时，仍按原规则回退或解除嵌入；Explorer 重建后可重新发现并附着新任务栏窗口。
- 嵌入窗口位置与尺寸未变化时不重复调用 `SetWindowPos`；Windows 10 也不重复调用带重绘的 `MoveWindow` 调整任务栏按钮区域。
- 透明顶层窗口方案、歌词轮询、无播放自动隐藏、设置与多显示器选择行为不变。

### 技术说明

- 附着结果拆分为 `Unavailable`、`Attached` 和 `AttachedPositionPending`。主窗口与镜像窗口只对 `Unavailable` 执行透明窗口回退；`AttachedPositionPending` 保留已建立的原生父子关系。
- 临时找不到任务栏或 Win10 容器时，仅当窗口、目标显示器和现有父窗口均仍有效才保留附着并重试；目标变化或句柄失效不会沿用旧任务栏。
- `EmbeddedTaskbarAnchor` 缓存最近一次成功提交的窗口物理边界和 Windows 10 任务列表目标边界；原生调用失败时不更新缓存，后续调用可继续重试。窗口、任务栏或父窗口变化以及 `Detach` 会清空缓存。
- 相同逻辑宽高不重复写入 WPF `Window.Width`/`Height`；DPI 与显示变化的既有事件驱动刷新链路保持不变。

### 兼容性

- 未修改 `settings.json`、WebView V1 消息、缓存格式、歌词检索、SMTC、热键或发布结构。
- 任务栏嵌入接口仅在 App 内部由布尔值调整为显式状态，设置与外部协议不受影响；Windows 10/11 的父窗口选择方式不变。

### 验证

- 定向验证通过：`EmbeddedTaskbar` 相关 App 测试 23/23；覆盖临时定位失败保持嵌入、不可用时回退、仅保留同一有效目标，以及原生边界调用去重。
- App 项目验证通过：219/219。
- 完整验证通过：Web 62/62、App 219/219、Core 134/134、Settings 契约、代码格式、验证输出与重启脚本回归均通过；日志位于 `tmp/verify-logs/20260821-105529410-4372-2f77d7508f4e43a382245cfe97dca846/`。
- `dotnet build TaskbarLyrics.sln --no-restore -t:Rebuild`：0 警告、0 错误；日志位于 `tmp/verify-logs/taskbar-embedding-attach-retry-solution-rebuild.log`。

### 后续事项

## 2026-08-21｜选择性合入任务栏嵌入显示方案

### 变更目的

将 `taskbar-integration` 分支 PR #38 的核心任务栏嵌入能力合入 `main`，同时避免把分支基于旧主线产生的播放状态、无输入隐藏、SMTC、频谱或歌词转场行为带回。嵌入模式作为默认关闭的独立显示机制，与现有透明顶层窗口方案并存。

### 用户影响

- 设置页新增「任务栏嵌入（测试版）」页面，可启用嵌入、选择左/中/右水平锚点，并调整嵌入宽度及水平、垂直偏移。
- 开启后，歌词窗口会嵌入当前所选显示器对应的任务栏；「全部显示器」和「选定显示器」继续按 `main` 的既有规则创建主窗口与镜像窗口。目标显示器没有任务栏窗口时，该屏自动回退到透明窗口定位，不会错误堆叠到主任务栏。
- 关闭后恢复原有透明窗口定位、锚点、偏移和置顶路径；旧设置继续保留且不被嵌入专属参数覆盖。
- `main` 已有的无播放自动隐藏、播放快照防抖、歌词/频谱呈现和多显示器选择行为保持不变。

### 技术说明

- 新增 `EmbeddedTaskbarAnchor`，通过 `SetParent` 将现有 WPF/WebView2 歌词窗口挂入任务栏窗口树，并由纯函数 `EmbeddedTaskbarLayoutCalculator` 完成水平锚点、垂直居中、DPI 物理像素换算和显示器相交面积计算。
- Win11 直接挂载目标显示器的 `Shell_TrayWnd` 或 `Shell_SecondaryTrayWnd`；Win10 挂载对应任务栏的 `ReBarWindow32`（回退 `WorkerW`），压缩并在 Detach/Dispose 时恢复该任务栏的任务列表。
- 主歌词窗口和每个 `LyricsMirrorWindow` 各自拥有锚定器，按 `DisplayMonitor.Bounds` 选择相交任务栏；切换显示器、关闭嵌入或释放窗口时恢复父窗口、原始窗口样式和任务列表尺寸。
- `AppSettings` 新增开关、嵌入宽度、锚点和两轴偏移字段；加载与保存时统一校验范围和未知枚举。`AppSettingsChangeSet` 将这些字段归入独立的运行时重定位变更，不触发歌词服务重建。
- 设置页继续使用原生 HTML/CSS/JavaScript 与 WebView V1 信封；嵌入参数支持实时预览并在 C# 边界再次校验。

## 2026-08-18｜频谱捕获线程在音频设备异常后自愈恢复

### 变更目的

### 用户影响

### 技术说明

- `CaptureLoop` 的 `catch` 块由 `break` 改为指数退避后 `continue`：首次失败 `100ms`、逐次倍增至上限 `2000ms`，成功后重置计数。

- `RunCaptureSession` 正常返回（设备变更或取消）后重置 `_consecutiveCaptureFailures`；`StopCaptureSession` 亦在停止时清零，确保再次 `Start` 从基线退避开始。
- `_lastError` 在重试期间保持可见，恢复成功后由 `RunCaptureSession` 清空；现有 `SPECTRUM` 诊断日志以 `5s` 节流覆盖错误边沿，无需新增日志。
- 未改变 `Start`/`Stop`/`Dispose` 生命周期状态机、COM 互操作边界、WebView 协议、设置或持久化。

### 兼容性

- `RetrySpectrumCapture` 手动重试路径行为不变；自动恢复与手动重试互不干扰。

解决检索歌词行与频谱互相衔接时翻滚过快，以及频谱进入前预定位可能产生下移或回弹感的问题，同时保持现有跨层转场模型不变。

### 用户影响

- 检索进入频谱、频谱退出到检索均改为与翻译模式相同的 `760ms` 翻滚节奏，衔接更舒缓一致。
- 频谱进入先在无动画准备态完成下方预定位，再单向上翻到最终位置，不再出现额外的下移或回弹。
- 频谱目标在进入动画期间重复刷新时只更新最新目标，不会让检索行与频谱反复回到起点争抢位置。
- 纯音乐频谱切歌时不会先翻入旧曲目的临时检索行；频谱保持到下一曲目身份到达，再直接翻滚到下一首的检索元数据。
- 检索阶段直接切歌时，新曲目的“歌曲名 - 歌手”按 `560ms` 标准单行节奏翻入，不再原地突变；同一曲目的元数据校正仍保持原位更新。
- 移除切歌后的独立 `900ms` 检索停留；快速歌词或频谱结果等待当前 `560ms` 检索翻滚完成后立即衔接，不再额外静止约 `340ms`。
- 普通歌词或消息与频谱之间的层切换仍为 `300ms`；减少动态效果、显式禁用动画、快速反向和最新帧优先行为保持不变。

### 技术说明

- `PresentationPlanner` 继续生成原有 `searchingToSpectrumRoll` / `layerSwitch` 计划，并通过 `durationMs` 区分检索相关的 `760ms` 与普通层切换的 `300ms`。
- `app.js` 将 Planner 时长写入统一的 `--layer-transition-duration`，CSS 不再为频谱进入和退出分别硬编码时长。
- 频谱进入显式分为 `spectrum-transitioning` 准备态和 `spectrum-entry-active` 动画态；准备态禁用 transition，Coordinator 持有的下一帧才启用位移与透明度转场。
- 活动的 `searchingToSpectrumRoll` 对重复频谱目标采用 latest-frame-wins：保留当前 generation 和首个 rAF，只覆盖 `pendingFrame`，完成时提交最新目标。
- 稳定 `spectrum` 场景使用 `trackId` 过滤同曲目的临时 `searching` 帧；不同身份的检索帧仍按原 `layerSwitch` 路径启动退出，不依赖可见歌词文案判断。
- `PresentationPlanner` 在 `searching → searching` 中以两个非空 `trackId` 是否变化区分切歌与同曲校正：切歌生成原有 `singleRoll`，同曲仍使用 `replaceInPlace` / `progressPatch`。
- 检索切歌翻滚活动期间，歌词和频谱统一采用 Coordinator 的 latest-frame-wins 等待完成事件；频谱目标携带执行上下文，完成后仍走原有 `searchingToSpectrumRoll`，不会退化成立即层替换。
- generation、rAF、fallback、`transitionend`、latest-frame-wins、频谱数据通道和跨层 DOM 结构均未改变。

### 兼容性

- WebView V1 envelope、场景和计划类型、歌词与翻译内部翻滚、设置存储及 Core 检索逻辑保持兼容；仅移除切歌检索完成后的额外静止等待。
- 未修改窗口定位、多显示器、频谱采集或发布结构。

## 2026-08-14｜Lyricify.Lyrics.Helper 头部竞态排查与引用还原

### 变更目的

### 技术说明

#### 头部竞态（真实缺陷，已提交 PR 待上游合入）

- `BaseApi` 在每次请求前对共享静态 `HttpClient.DefaultRequestHeaders` 执行 `Clear()` + 重写，多源并行时一个音源的 `SetRequestHeaders()` 会覆盖另一个音源尚未发出的请求头部。

- 已向 `WXRIW/Lyricify-Lyrics-Helper` 提交 Issue 和 PR。

#### 代理 IP 限流（主要根因，误判为头部竞态）

- QQ 音乐搜索 API 在同一 IP 短时间内多次请求后返回 `code=2001`（限流码）和空结果，为 IP 级限流而非 per-query。
- 冷却时间超过 3 分钟，期间所有查询均返回空；代理出口的共享 IP 更易触发。
- 直连（绕过代理）访问 QQ 音乐完全正常，`code=0` 稳定返回结果。

- `TaskbarLyrics.Core.csproj` 由 `ProjectReference`（本地 fork）还原为 `PackageReference`（nuget.org `0.2.0`）。

### 技术说明

- Core 根据 `LyricSyllable` 的相对偏移、时长及其在原始歌词文本中的位置计算可空 `WordScanProgress`；英文空格等未包含在 segment 文本中的字符仍会映射回原句位置。
- App 仅在开关开启时把逐词进度加入歌词 WebView V1 payload；开关切换不会重建 `LyricSyncService` 或触发网络请求。
- WebView 使用现有 `--primary` / `--secondary` 颜色生成文字宽度内的裁剪渐变；进度为 `null` 时移除扫描状态，保留旧渲染路径。
- 切行期间的 promotion 状态实时消费同一句的最新逐词进度，扫描从翻滚开始即同步推进；下一句仍通过 queued frame 串行处理，不改变原有字号与位移动画。
- 晋升行从转场开始即使用第一行的原生字体度量，仅通过 `scale` 从第二行视觉尺寸过渡到 `1`，避免逐帧小数字号与转场结束重新栅格化造成清晰度和视觉字重跳变。
- 扫描显示使用两层普通 `color` 文字与互补硬裁剪，次色复用主色 RGB 并将 alpha 调整为主色的 60%，继续避免透明填充与 `background-clip: text`；播放时由 WebView 在相邻进度样本间执行 90ms 线性插值，暂停时立即移除插值并冻结在当前值。SMTC 在播放与暂停相互切换且时间线尚未刷新时会保留最后已展示位置，刷新后再接受真实播放、暂停或拖动位置，既避免暂停时回退到上一个逐词节点，也避免恢复播放时把暂停时长错误计入外推位置。静止时清理行/轨道 transform，并仅在转场期间启用 `will-change`，让第一行恢复与第二行一致的字体栅格化路径。
- 超长当前行的主色层和次色层共用一个裁剪视口与文字轨道；WebView 缓存自然文本宽度，以逐词进度估算扫描头位置，在视口 65% 锚点后计算受限横向偏移，并按物理像素对齐。连续播放只在短步进期间对位移执行 90ms 插值，暂停、跳播、换行、转场取消和进度缺失均立即定位或清理，不启用循环跑马灯。

## 2026-07-29｜完善 PerMonitorV2 运行时 DPI 切换并强化可观测性与覆盖

### 变更目的

完整修复应用运行期间切换系统缩放时的一组关联问题：窗口和 WebView2 内容模糊、托盘菜单命中失效，以及启用 PerMonitorV2 后歌词窗口在 100% 与 150% 间双向切换时裁切或消失；并落实审查结论，避免 WebView2 控制器内部接口变化或原生窗口边界提交失败时静默退化，补齐缩放档位回归覆盖。

### 用户影响

- 运行中切换系统显示缩放时，歌词窗口、设置页、SMTC 监视器、频谱调试与托盘菜单按当前 DPI 渲染，托盘菜单保持正确命中。
- DPI 变化与显示设置变化现在合并为一次延迟布局刷新，等待 Windows 完成顶层窗口和 WebView2 子 HWND 的 DPI 通知及 WPF 实际布局后，再更新尺寸、任务栏锚点和网页样式。
- 移除 DPI 回调中的同步强制布局，避免 WebView2 在新栅格化比例与旧控制器边界并存时进入不可恢复的裁切或隐藏状态。
- 每次锚定都以当前窗口 DPI 将完整逻辑边界换算为物理像素并提交给原生窗口，100%→150% 与 150%→100% 使用同一条边界更新路径，不会沿用切换前的物理尺寸。
- 任务栏定位改为读取主显示器物理矩形，并按歌词窗口当前 DPI 统一换算为 WPF 逻辑单位，避免运行时缩放后混用物理像素与 DIP。
- 若 WebView2 WPF 宿主无法暴露 DPI 栅格化控制器，或原生窗口物理边界提交失败，应用会写入一次可定位的 DPI 诊断；宿主仍通过 WPF DPI/显示设置事件执行基础刷新。

### 技术说明

- 根因一：自定义 `Program.Main` 未在创建 WPF `App` 前声明 DPI 感知，进程以 System DPI 模式运行；系统只能缩放启动时生成的位图，导致内容模糊且原生命中坐标错位。入口现在通过 `SetProcessDpiAwarenessContext(-4)` 显式启用 PerMonitorV2。
- 根因二：PerMonitorV2 生效后，Windows、WPF 与 WebView2 子 HWND 的 DPI 通知并非同时完成；同时 WPF `Height` 的逻辑值在切换前后均为 44 DIP 时不会重新提交原生高度，曾出现窗口 DPI 已降至 96、物理高度却仍保留 150% 下 66 px 的状态，窗口底部因此超出屏幕。
- `MainWindow` 通过线程安全的待处理标记合并 `OnDpiChanged`、`DisplaySettingsChanged` 与 WebView2 `RasterizationScaleChanged`，在 `DispatcherPriority.ContextIdle` 延迟执行完整刷新；浏览器确认自身栅格化比例变化后会再合并补充一次刷新。
- `TaskbarPlacementService` 以 `GetDpiForWindow` 作为运行时缩放的权威值，同时更新 WPF 逻辑位置和 `SetWindowPos` 物理边界，消除 WPF `Height` 属性未变化时不会重新提交原生高度的问题。
- 删除冗余的 `SizeChanged → AnchorToTaskbar` 回调，避免锚定代码修改窗口高度时再次进入锚定流程。
- `TaskbarPlacementService` 使用 `MonitorFromPoint`/`GetMonitorInfo` 获取主屏物理边界，并在单一命名边界完成像素到 DIP 的转换；原 `SystemParameters` 路径仅保留为原生查询失败时的安全回退。
- 将 WebView2 控制器获取整理为带失败原因的能力检测；反射访问内部 WPF 宿主失败时记录 WebView2 程序集版本和回退路径，而不让歌词 WebView 初始化失败。
- 检查 `SetWindowPos` 返回值，并在首次失败时记录 Win32 错误码、目标物理边界和当前像素比例，避免高频锚定过程重复写日志。
- 将歌词窗口边界测试由 100%/150% 扩展为 100%/125%/150%/200%，验证像素对齐后的窗口始终位于物理屏幕范围内。

### 兼容性

- `settings.json`、WebView V1 信封、歌词脚本注入标记、缓存和用户数据均无变化。
- 进程 DPI 感知从 System 提升为 PerMonitorV2；固定 DPI 下的尺寸、锚点、置顶和显隐语义保持不变，变化集中在运行时 DPI 变更和多显示器 DPI 边界。
- 反射控制器不可用时保留既有 WPF DPI 与显示设置刷新路径；新增日志仅用于诊断。

### 验证

- `scripts/verify.ps1` 通过：Web 14、App 64、Core 26、设置契约与代码格式检查全部通过。
- `dotnet build TaskbarLyrics.sln --no-restore`：0 个警告、0 个错误。

- 新增同一 420×44 DIP 窗口在 100% 与 150% 下分别提交 420×44 px 和 630×66 px 的双向边界回归测试，并扩展至 100%/125%/150%/200% 四档覆盖。
- 人工验证通过：100%→150%→100% 双向切换后歌词完整显示，未再发生裁切或消失；此前的页面模糊与托盘菜单点击失效问题未再复现。
