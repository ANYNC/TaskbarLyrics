# 横向任务栏避让：验证记录

## 范围与复现

基线：`eb3294b7469dcba72fec3b236725b745185c4703`。Windows 11 横向嵌入模式原先只把歌词窗口限制在整条任务栏内；当居中图标增多、搜索框占用变大，或歌词窗口宽度超过剩余空白时，长歌词会绘制到开始、搜索及应用按钮上。

本次根据可见交互控件的实际范围选择空白区间，保留 8 DIP 间距并限制实际窗口宽度。剩余区间不足 100 DIP，或没有可用的新鲜几何快照时，原生歌词表面临时缩为零，之后自动恢复；不改写用户配置宽度。浮窗、Windows 10 与竖向任务栏的既有定位路径不应用此横向策略。

与 PR #37 的关系：该 PR 新增可选的“自动跟随图标”锚点和过渡动画；本次修正现有左/中/右锚点的嵌入窗口边界，不增加设置项、枚举值或动画。

## 可重复运行的原生检查

```powershell
dotnet run -c Release --project TaskbarLyrics.Diagnostics -- --taskbar-space verify
dotnet run -c Release --project TaskbarLyrics.Diagnostics -- --taskbar-space benchmark 15
```

原生检查使用实际生产定位器和读取器，并临时创建透明窗口及一个自动关闭的最小化任务栏图标。检查图标出现／关闭时的动态边界、空间耗尽后恢复、负坐标父窗口，以及竖向定位绕过横向检测。它不启动音乐服务，不访问用户配置数据库，不重启 Explorer，也不更改任务栏设置。

最终 Release 原生检查五个阶段通过：任务栏图标增加时，实际歌词宽度从 366 px 缩为 312 px，关闭图标后恢复到 366 px，三个状态都保留 10 px 间距；隔离父窗口中验证了零面积隐藏、负坐标下恢复，以及 60 px 宽竖向定位不启动横向读取器。

性能命令交替运行六组相同节奏的客户端试验：保留调度器但不查询 UIA、原始宽泛子树查询、Explorer 子树查询，再反向重复；每组 15 秒。先核对两个读取器识别的占用区域一致。输出成功查询次数、尝试次数、临时错误类型、查询延迟、客户端 CPU 和分配量；临时错误不从报告中抹除。

这里的 CPU 仅属于诊断查询客户端，按逻辑处理器数量归一化。它不代表整个歌词应用、Explorer 服务端、GPU、游戏帧率或电池续航的净变化。延迟包含跨进程等待，桌面负载会使结果变化，不据此承诺固定收益。

### 本机 Release 采样

完整六组原始数据见 [taskbar-space-benchmark.json](taskbar-space-benchmark.json)，每组 15 秒、每种模式两组，顺序交替；最终采样各组临时错误计数均为零。

| 模式 | 查询延迟中位数（两组） | 客户端 CPU（两组） | 每次查询分配量约值 |
| --- | --- | --- | --- |
| 只保留调度器，不读取 UIA | 0.001–0.002 ms | 0.0097–0.0260% | — |
| 原始宽泛子树 | 41.343 / 178.503 ms | 0.0813 / 0.2173% | 179 KiB |
| Explorer 子树 | 35.305 / 54.903 ms | 0.0389 / 0.1297% | 111 KiB |

原始数据的 `AllocatedMB` 按 1,048,576 字节换算。此采样中分配量约减少 38%。桌面负载明显影响延迟与 CPU，不能把不同组之间的差值当作整个应用的净收益或通用性能保证。保留 500 ms 节流以获得可预测的恢复响应；事件驱动失效可作为后续优化单独评估。

## 仍需在其他设备复核

- 本机没有第二个物理显示器；负坐标和不同缩放的计算已有自动及原生父窗口检查，但不能替代真实混合 DPI 多屏切换。
- 未实际重启用户的 Explorer；句柄、矩形、失效读取和迟到结果已通过可控故障验证。
- 未在真实 Windows 10 或第三方修改的任务栏上测试。Windows 10 和竖向定位分支保持原路径；原生检查验证了竖向绕过，不代表所有第三方任务栏兼容。
- 500 ms 检测存在响应间隔。暂时读取失败时最多沿用两秒内的匹配快照，随后隐藏；单次未返回的原生调用不会造成查询堆积或阻塞歌词调度线程。
